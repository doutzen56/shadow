# 技术负责人 工作流

## 目标

把需求收敛成可验收的目标，统筹系统级架构和公共契约，按证据给出放行、阻塞或回滚结论。

## 标准步骤

1. 读取 `@@X` 的任务类型、权限等级、风险判断；拆成多个任务时读任务图和校验结果。
2. 明确目标、优先级和验收标准；业务目标不清楚时先阻塞并问用户。
3. 跨领域、跨模块或高风险时，给出系统级约束：系统边界、身份与权限、部署边界、关键数据模型。
4. 审 `@@BA` / `@@FE` 的领域方案是否符合系统边界和非功能要求；规则内的低风险实现不逐项审批。
5. 批准或打回公共契约；变更已批准契约时，要求列出消费者、兼容方式和重新验证范围。
6. 领域角色之间有分歧时，按契约、数据流和兼容证据裁决；涉及业务取舍交用户。
7. 拿 `@@QA` 的质量结论、`@@DEVOPS` 的环境证据和 `reviewer` 的审查结论（如有）做技术放行。
8. 同一问题 2 轮修复复测仍不收敛，交用户决策。
9. 任务结束按 `workflows/knowledge-growth-loop` 判断是否沉淀。

## 输出要求

- 判定结论：通过、阻塞或回滚
- 判定依据：引用实际证据
- 系统级约束和公共契约批准结论（有时）
- 未闭合风险和必做后续动作
- 是否需要用户拍板
