# HX.Matching 线程池饥饿事故经验教训

## 事故摘要

现象包括：收银台无法打开、订单无法提交、网关大量超时、Redis 客户端整池不可用、RabbitMQ 心跳丢失与握手超时。

最终判断：Redis、RabbitMQ、SQL Server 和主机资源都不是第一根因。根因是应用进程内在高并发请求路径上持有全局锁并同步查询分表元数据，导致线程池饥饿。其他基础设施异常大多是线程池无法及时调度后的连带现象。

## 根因链

1. 每个请求进入分表元数据预热逻辑。
2. 逻辑在全局锁内同步查询数据库表信息。
3. 单次查询偶发抖动时，后续请求全部串行排队。
4. 阻塞线程数超过线程池最小线程数。
5. 线程注入速度追不上请求堆积速度。
6. Redis 探活、RabbitMQ 心跳、业务请求和回调任务都排不上线程。
7. 外部表现为缓存不可用、消息队列断连、网关超时、订单卡住。

## 关键教训

### 主机指标正常不代表应用健康

事故期间主机 CPU 和内存并不紧张，数据库也没有表现为根因级瓶颈。线程池饥饿时，线程阻塞在同步等待中，不一定消耗 CPU。因此不能只依赖 CPU、内存和数据库等待判断系统健康。

### 同步阻塞会放大基础设施故障假象

Redis 和 RabbitMQ 的异常可能只是应用线程池无法调度造成的假象。排查时不能只盯着报错最多的外部组件，要判断它是否是根因还是受害者。

### 热路径不能在锁内访问数据库

高并发请求路径上，锁内访问数据库是高风险模式。平均耗时很低也不安全，因为一次秒级抖动就可能把所有请求串行阻塞。

### 单实例后台任务进程需要额外关注

后台任务进程集中承载消息消费、回调、统计和超时任务。它不是普通后台服务，一旦饿死，前台接口可能仍然看似健康，但订单推进会停止。

## 修复原则

- 分表元数据缓存需要有限有效期。
- 缓存新鲜时直接返回，不进入锁，不访问数据库。
- 到期刷新应尽量后台单飞执行，请求线程优先使用旧值。
- 线程池最小线程数可以作为防抖兜底，但不能替代消除同步阻塞。
- 健康检查不能只返回固定成功，需要测量线程池排队延迟。
- 请求必须有服务端超时，不能等网关先超时。
- 消息消费者不能随意释放进程级共享连接。
- 缓存故障时应有进程内兜底和回源闸门，不能无限回源数据库。

## 以后排查清单

遇到“CPU 空闲但请求超时”时，优先检查：

1. 线程池排队延迟。
2. 阻塞线程数量。
3. 是否存在锁内同步数据库或缓存调用。
4. 是否存在同步等待异步任务的代码。
5. Redis 和 RabbitMQ 异常是否可能是线程池饥饿的连带现象。
6. 后台任务进程是否仍在消费消息。
7. 网关超时前，服务端是否主动取消请求。

## SimpX 复用方式

这个案例应作为企业稳定型和性能优先型项目的高价值样本。任何涉及高并发热路径、分表、缓存、消息队列和后台任务的项目，都可以用这份经验做风险审查。
