# HX.Matching 服务边界

## 当前边界判断

HX.Matching 是分层单体，但边界不是严格的领域驱动或纯净架构。实际边界以运行宿主和项目职责为主。

## 项目职责

| 项目 | 当前职责 | 边界建议 |
| --- | --- | --- |
| ServiceCore | 核心业务、撮合、渠道、缓存、搜索、统计 | 一阶段保持事实核心，不急于拆分 |
| Service | 名义服务层，实际较薄 | 后续需判断保留、合并或重新定位 |
| Repository | SqlSugar 仓储基础 | 保持数据访问基础职责，避免业务规则下沉 |
| Model | 实体、枚举、请求响应、搜索文档 | 避免吸收基础设施依赖和运行时逻辑 |
| Infrastructure | 缓存、消息、认证、扩展、工具 | 放横切能力，不放具体业务判断 |
| Tasks | 定时任务定义 | 任务编排可在此，具体业务规则仍回到核心服务 |

## ServiceCore 治理重点

ServiceCore 是最重要的治理对象，但不建议一阶段直接大拆。更合适的顺序是：

1. 先按业务域标记目录和服务职责。
2. 再识别高风险链路：订单、资金、回调、撮合、渠道。
3. 然后给新增功能建立放置规则。
4. 最后再考虑是否拆目录、拆项目或抽象接口。

## 新功能放置原则

- 对外接口入口放对应宿主。
- 业务规则放 ServiceCore。
- 数据结构放 Model。
- 数据访问基础放 Repository。
- 缓存、消息、认证、限流等横切能力放 Infrastructure。
- 定时任务触发和调度放 Tasks，运行在 Quartz.Job。

## 代码审查关注点

涉及以下内容时必须扩大审查范围：

- 订单状态变化。
- 金额、余额、手续费和汇率。
- 商户、渠道、供应商规则。
- 回调通知和重试。
- 分表、缓存和搜索索引。
- 后台任务和消息消费者。
- 对外接口签名和响应契约。

## 对 SimpX 的沉淀价值

这个项目可以作为“业务交付优先的企业系统如何逐步治理边界”的样本。SimpX 不应强行套用理想架构，而应先识别现有事实边界，再逐步制定可落地的改造规则。
