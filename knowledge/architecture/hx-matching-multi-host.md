# HX.Matching 单仓五宿主架构

## 背景

HX.Matching 是单个解决方案维护多个运行宿主的系统。源码统一管理，但运行时拆成多个进程和部署产物。

这种结构适合业务复杂、入口多、稳定性要求高的系统：不同入口可以独立部署、独立限流、独立超时，同时复用同一套核心业务能力。

## 五宿主划分

| 宿主 | 主要职责 | 稳定性意义 |
| --- | --- | --- |
| 平台管理端 | 后台运营、配置、统计、导出、系统管理 | 将管理类长任务与开放接口热路径隔离 |
| 商户后台 | 商户自助管理、订单和报表 | 将商户管理动作与商户开放接口隔离 |
| 商户开放接口 | 代收、代付、查单、收银台 | 作为商户热路径，需要低延迟和明确超时 |
| 合作方互通接口 | 合作方下单、撮合查询、挂单 | 与撮合链路耦合更紧，超时窗口更长 |
| 后台任务进程 | 定时任务、消息消费、回调、统计、告警 | 异步中枢，单实例风险最高 |

## 架构收益

- 对外开放接口可以比后台管理接口拥有更严格的超时策略。
- 管理端导出、报表和人工操作不会直接拖慢收银台热路径。
- 消息消费者集中在后台任务进程，便于控制异步链路和回调处理。
- 多个部署产物可以分别发布和回滚。

## 架构风险

- 共享核心层过重，容易让所有宿主间接耦合。
- 后台任务进程集中承载消息消费，单实例故障会影响撮合、回调、超时和统计。
- 远程配置复用时，监听地址、依赖注入扫描和开关配置容易互相影响。
- 多宿主共享业务代码时，修改 ServiceCore 需要同时评估五个宿主的影响。

## SimpX 使用方式

遇到 HX.Matching 的需求时，先判断改动影响哪个宿主：

- 改商户下单、收银台、商户验签，优先看商户开放接口。
- 改合作方下单、收款账户、挂单，优先看合作方互通接口。
- 改后台配置、统计、导出，优先看平台管理端。
- 改商户侧管理能力，优先看商户后台。
- 改回调、消费、超时、定时任务，优先看后台任务进程。

再判断是否触碰 ServiceCore。只要触碰 ServiceCore，就要做跨宿主影响评估。
