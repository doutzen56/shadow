# HX.Matching 系统边界

## 边界总览

HX.Matching 是单仓多宿主系统。不同宿主共享核心业务层，但运行时职责不同。边界分析的目标不是追求形式上的纯净分层，而是避免错误地把热路径、后台治理、异步消费和管理操作混在一起。

## 宿主边界

### 平台管理端

路径：`E:\work\撮合项目\HX.Matching.Admin.WebApi`

职责：

- 平台运营后台接口。
- 商户、供应商、渠道、订单、统计、权限和系统配置管理。
- SignalR 通知、验证码、限流、数据保护、离线导出入口。
- 发布部分消息，部分后台服务也在此进程内运行。

边界：

- 允许承载后台报表、导出和运营动作。
- 不应承载商户下单热路径。
- 不应抢占任务进程的集中消息消费职责。

### 商户后台

路径：`E:\work\撮合项目\HX.Matching.MerchantAdmin.WebApi`

职责：

- 商户自助后台接口。
- 商户登录、订单查询、余额、报表和账号管理。
- 商户缓存预加载和缓存失效订阅。

边界：

- 面向商户管理操作，不直接承担开放接口下单链路。
- 请求超时策略比开放接口宽松，适合报表和管理动作。

### 商户开放接口

路径：`E:\work\撮合项目\HX.Matching.MerchantApi`

职责：

- 商户代收、代付、查单和收银台。
- 商户验签、商户状态校验、订单创建和供应商链路调用。
- 热路径接口设置更短的服务端超时。

边界：

- 是商户侧核心入口，应优先保证低延迟和可用性。
- 不注册主要消息消费者，避免与后台任务重复消费。
- 不承担管理端报表和长任务。

### 合作方互通接口

路径：`E:\work\撮合项目\HX.Matching.PartnerApi`

职责：

- 合作方下单、查收款账户、卖家挂单和订单查询。
- 与撮合链路关系更紧，下单接口可能同步等待撮合与供应商拉单。
- 使用独立默认端口，避免复用远程配置导致监听地址被覆盖。

边界：

- 本进程只发布订单相关消息，不承载集中消费。
- 签名拼串与响应命名存在故意差异，不能随意修改。
- 超时策略需要保留撮合窗口，同时避免请求无限挂起。

### 后台任务进程

路径：`E:\work\撮合项目\HX.Matching.Quartz.Job`

职责：

- 定时任务调度。
- 消息队列消费者。
- 商户回调、渠道回调查询、统计、导出、撮合消费、超时处理。
- Telegram 通知。

边界：

- 是异步中枢，单实例风险高。
- 不在负载均衡后面时，就绪探针用于告警而不是摘流。
- 共享连接和消费者生命周期不能随意释放，否则会影响全部异步链路。

## 核心层边界

### 业务核心

`HX.Matching.ServiceCore` 是事实上的业务核心，包含撮合、渠道适配、缓存封装、搜索、统计和部分后台服务。

边界风险：该项目过重，既有业务规则也有基础设施适配，后续治理应优先做目录和职责边界梳理，而不是立即拆项目。

### 数据模型

`HX.Matching.Model` 承载实体、枚举、请求响应和搜索文档模型。

边界风险：模型层不应继续吸收基础设施细节，新增模型应尽量保持数据结构职责。

### 仓储基础

`HX.Matching.Repository` 提供 SqlSugar 仓储能力和分表相关基础。

边界风险：仓储与服务在实际使用中耦合较强，做架构治理前需要先分析调用链。

### 基础设施

`HX.Matching.Infrastructure` 提供缓存、消息、认证、限流、异常处理、帮助类和扩展方法。

边界风险：基础设施承担很多横切能力，新增功能时应避免把业务规则继续下沉到这里。

## 边界治理原则

- 改热路径先看 MerchantApi 和 PartnerApi。
- 改异步链路先看 Quartz.Job 与消息消费者。
- 改管理功能先看 Admin 与 MerchantAdmin。
- 改核心规则先看 ServiceCore，再追踪 Model、Repository 和 Infrastructure。
- 不把业务仓库的真实代码搬进 SimpX，只沉淀边界、方法和经验。
