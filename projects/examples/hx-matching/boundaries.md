# HX.Matching 系统边界

## 边界总览

HX.Matching 是单仓多宿主系统。不同宿主共享核心业务层，但运行时职责不同。边界分析的目标不是追求形式上的纯净分层，而是避免错误地把热路径、后台治理、异步消费和管理操作混在一起。

## 宿主边界

下面只写建档时已有宿主的边界经验，不是完整项目清单。仓库里有哪些项目，以根目录的 `HX.Matching.sln` 为准。阶段性的约束（比如某一阶段哪些项目不许动），由用户开工时在对话里交代，不写在这里。

### 平台管理端

路径：`HX.Matching.Admin.WebApi`

职责：

- 平台运营后台接口。
- 商户、供应商、渠道、订单、统计、权限和系统配置管理。
- SignalR 通知、验证码、限流、数据保护、离线导出入口。
- 发布部分消息，部分后台服务也在此进程内运行。
- 可保留渠道回调兼容入口；默认库即首库/现网，**不**承担多租户新租户切库。

边界：

- 允许承载后台报表、导出和运营动作。
- 不应承载商户下单热路径。
- 不应抢占任务进程的集中消息消费职责。
- 多租户新租户渠道回调应打 MerchantApi「商户下单」绑定域，不要依赖本宿主切租户库。

### 商户后台

路径：`HX.Matching.MerchantAdmin.WebApi`

职责：

- 商户自助后台接口。
- 商户登录、订单查询、余额、报表和账号管理。
- 商户缓存预加载和缓存失效订阅。

边界：

- 面向商户管理操作，不直接承担开放接口下单链路。
- 请求超时策略比开放接口宽松，适合报表和管理动作。

### 商户开放接口

路径：`HX.Matching.MerchantApi`

职责：

- 商户代收、代付、查单和收银台。
- 商户验签、商户状态校验、订单创建和供应商链路调用。
- 渠道异步回调主入口（`/channelcallback/...`）：按「商户下单 / 收银台」绑定域 Host 定租户。
- 热路径接口设置更短的服务端超时。

边界：

- 是商户侧核心入口，应优先保证低延迟和可用性。
- 不注册主要消息消费者，避免与后台任务重复消费。
- 不承担管理端报表和长任务。
- 定租户只认 Host + Purpose；`merchantCode` 只校验归属。细则见 `flows-multitenant-and-review.md`。

### 合作方互通接口

路径：`HX.Matching.PartnerApi`

职责：

- 合作方下单、查收款账户、卖家挂单和订单查询。
- 与撮合链路关系更紧，下单接口可能同步等待撮合与供应商拉单。
- 使用独立默认端口，避免复用远程配置导致监听地址被覆盖。

边界：

- 本进程只发布订单相关消息，不承载集中消费。
- 签名拼串与响应命名存在故意差异，不能随意修改。
- 超时策略需要保留撮合窗口，同时避免请求无限挂起。

### 后台任务进程

路径：`HX.Matching.Quartz.Job`

职责：

- 定时任务调度。
- 消息队列消费者。
- 商户回调、渠道回调查询、统计、导出、撮合消费、超时处理。
- Telegram 通知。

边界：

- 是异步中枢，单实例风险高。
- 不在负载均衡后面时，就绪探针用于告警而不是摘流。
- 共享连接和消费者生命周期不能随意释放，否则会影响全部异步链路。

## 核心层边界

### 业务核心

`HX.Matching.ServiceCore` 是事实上的业务核心，包含撮合、渠道适配、缓存封装、搜索、统计和部分后台服务。

边界风险：该项目过重，既有业务规则也有基础设施适配，后续治理应优先做目录和职责边界梳理，而不是立即拆项目。

### 数据模型

`HX.Matching.Model` 承载实体、枚举、请求响应和搜索文档模型。

边界风险：模型层不应继续吸收基础设施细节，新增模型应尽量保持数据结构职责。

### 仓储基础

`HX.Matching.Repository` 提供 SqlSugar 仓储能力和分表相关基础。

边界风险：仓储与服务在实际使用中耦合较强，做架构治理前需要先分析调用链。

### 基础设施

`HX.Matching.Infrastructure` 提供缓存、消息、认证、限流、异常处理、帮助类和扩展方法。

边界风险：基础设施承担很多横切能力，新增功能时应避免把业务规则继续下沉到这里。

## 业务边界

### 撮合单审核只归总后台

原则：只有总后台（平台）能审核撮合单，租户后台不审核。

- 一审、二审、终审、转派、撮合客服配置，都只放在总后台菜单和接口里（V2 路由 `/api/v2/platform/review/...`、`/api/v2/platform/customerService/...`）。
- 租户后台只保留和自己订单有关的查看和处理：撮合超时订单、渠道凭证超时（含取消充值单、取消记录）、撮合补充凭证、撮合审单查询（只看详情和导出，不放「跳转终审」）。
- 租户侧旧的审核和客服接口暂时保留，但由 `[TenantSelfReviewOnly]` 按租户的 `ReviewOwner` 拦截：新租户默认 `Platform`，调用直接返回 403；只有存量首租户 T0001 还是 `Tenant`，作为过渡期自审。T0001 迁到平台审核后，这批接口可以下线。
- 租户审单查询的详情、AI 识别、历史凭证是只读接口，不走 `ReviewOwner` 拦截，只看审单相关权限。
- 新增撮合审核相关功能，默认做在总后台；如果要在租户侧加审核动作，先找用户拍板。

### V2 多租户改动与 V1 隔离（用户 2026-10-21）

原则：V2 / 多租户改造默认不牵连 V1；共享代码优先保证 V1 行为不变；若 V1 也必须同步改行为，先让用户拍板。

- V1 宿主：`HX.Matching.Admin.WebApi`（默认库=首库/现网）。
- V2 宿主：`HX.Matching.AdminV2.WebApi`（总后台 + 租户后台）。
- 共享层（ServiceCore 等）新增多租户行为时，应用租户上下文 / `MultiTenantRuntime.Enabled` / V2 专用入口隔离；不要改 V1 默认路径语义。
- 详见 `knowledge/decisions/2026/ADR-2026-10-21-hx-matching-v2-mt-not-break-v1.md`。

### 预付撮合费仅非首租户（用户 2026-10-21）

原则：预付撮合费是 V2 能力，**不得影响 V1 / 首租户 T0001（LegacyTenantCode）**。

- 门禁、实时扣费、对账补扣、停撮合 Redis/公告：仅对非 T0001 生效。
- Job 虽恒开多租户，共享撮合路径对 T0001 仍整条豁免；新租户照常校验余额与佣金模式。
- 已失败的旧单不强制重推；部署后新下单即可按新规则走。

## 边界治理原则

- 改热路径先看 MerchantApi 和 PartnerApi。
- 改异步链路先看 Quartz.Job 与消息消费者。
- 改管理功能先看 Admin 与 MerchantAdmin。
- 改核心规则先看 ServiceCore，再追踪 Model、Repository 和 Infrastructure。
- 不把业务仓库的真实代码搬进 SimpX，只沉淀边界、方法和经验。
