# 代码审查

## 通用前置检查

执行本流程前，必须先完成 `workflows/_shared/` 中的任务入口、权限、证据、验证、角色交接和完成检查。

## 目标

在交付前识别高风险缺陷并给出放行建议。

## 输入

- 变更范围与目标
- `@@BE` / `@@FE` 断言清单和变更文件清单
- 引用的契约和版本（如有）
- `@@QA` 验证结果（如有）

## 标准步骤

1. 按改动范围选审查人：高风险改动由 `reviewer` 审查；有前端改动时 `@@FE` 做前端专业评审；改了公共契约时 `@@TL` 审查契约兼容。
2. 按行为正确性、安全性、数据或状态一致性、兼容性、稳定性审查；有契约时核对实现是否符合契约版本，有多个任务时核对同文件冲突和越界修改。
3. 输出问题清单（高/中/低）和证据。
4. `@@BE` / `@@FE` 对高风险项给修复动作。
5. `@@QA` 对修复项复测关键断言。
6. `@@TL` 基于证据给放行结论。
7. `@@X` 汇总审查发现，`@@TL` 按 `knowledge-growth-loop` 判断是否形成反例、审查清单或模式卡。

## 输出

- 审查问题清单
- 修复与复测结果
- 放行建议（通过/阻塞/回滚）

要落文件时用 `templates/review-report/README.md`。示例：`workflows/code-review/examples/hx-matching-funds-change.md`。

## 收口检查

- 高风险问题未闭合不得通过。
- 证据不足不得通过。
- 公共契约变更没列消费者和兼容方式不得通过。
- 同一问题修复-复测超过 2 轮，交用户决策。
- 可复用审查发现进入 `knowledge-growth-loop`。
