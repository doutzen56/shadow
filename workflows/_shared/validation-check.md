# 验证检查

## 用途

本文件定义测试角色如何按任务级别设计验证。它服务所有工作流，不只服务功能开发和发布。

## 谁负责什么

- 开发者（`@@BE` / `@@FE`）：自验证，证明自己先跑过变更点和主路径；有页面改动时 `@@FE` 自验证也默认用浏览器工具走主路径。
- `@@QA`：测试设计、断言比对、场景验证、契约一致性、集成和回归验证、质量结论；有页面项时在本阶段按固定顺序自动调用：先 Playwright，仅当其不可用时再调 Cursor 内置 Browser；不依赖用户再说一遍。
- `@@DEVOPS`：环境准备、组件连通、部署冒烟，给 `@@QA` 环境可用证据；含页面验证时还要给出可打开的地址和登录方式（密钥不进报告明文）。
- 三类证据分开记录；环境失败和产品逻辑失败分开归因。

## 验证来源

`@@QA` 设计验证时，不能只执行开发者的自验证断言。验证项至少来自：

- `@@TL` 的验收口径。
- `@@BA` / `@@FE` 的边界、风险和验证重点。
- `@@BE` / `@@FE` 的变更范围、自验证断言和失败判定。
- 引用的契约（有时）：实现是否符合已批准的契约版本。
- 项目常见风险：资金、订单、权限、登录、用户数据、缓存、异步、第三方回调、历史兼容。

## 分级验证

- 快线任务：改文案、注释、普通 Markdown。只确认修改点，未跑业务验证时要明说。
- 低风险小改：验证变更点和一条主路径，能跑命令就记录命令。
- 普通功能：覆盖主链路、至少一条失败路径和任务涉及组件。
- 重要需求：补充 3-7 个真实业务场景。
- 高风险需求：在重要需求基础上，必须有 `@@TL` 验收口径、`@@BA` 风险结论和 `reviewer` 复核建议。只有 `@@TL` 或用户明确裁剪时，才能跳过 reviewer，并说明原因。

## 多任务验证

拆成两个以上任务时：

- 每个任务先有自己的自验证和断言比对。
- 合并后再做一次集成验证：构建通过、任务之间的接口按契约对得上、没有互相覆盖改动。
- 汇总时按任务列出结果，不能用一个总的"通过"盖住某个任务的失败或未验证项。

## 重要需求触发条件

命中以下任一条件时，按重要需求处理：

- 涉及资金、订单状态、权限、登录、用户数据或状态流。
- 涉及 DB、Redis、ES、MQ、后台任务或第三方回调。
- 涉及幂等、重试、补偿、异步一致性或历史兼容。
- 改动影响主业务路径，或失败后会造成错账、重复处理、权限越权、数据丢失、用户不可用。

## 场景验证格式

每个真实业务场景必须包含：

- 场景目标。
- 前置数据。
- 操作步骤。
- 期望状态。
- 实际证据：接口响应、DB、Redis、ES、MQ、日志、后台任务结果、页面操作结果/截图，或人工确认。
- 清理方式。
- 未覆盖风险。

## 页面验证（默认自动调用，顺序固定）

命中以下任一条件时，`@@QA`（以及有 UI 改动时的 `@@FE` 自验证）必须自动执行页面项：

- 改动 Web.Admin、Web.System 或其他前端页面。
- 断言或验收口径含界面展示、交互、菜单/按钮可见性、表单提交后的页面反馈。
- 重要或高风险场景需要从用户可见路径证明行为。

工具调用顺序（必须按序，不得写成「Playwright 或 Browser」任选）：

1. 先调用已启用的 Playwright（插件或 MCP）。
2. 仅当 Playwright 未安装、未启用或调用失败时，再调用 Cursor 内置 Browser。
3. 两者都不可用，或页面地址未知、无法登录时，结论只能是「验证阻塞」，并写清卡在第几步。

要求：

- 进入验证职责阶段即按上序执行，不要求用户写「用 Playwright」或再召唤 `@@X`。
- 证据必须写明实际落在第 1 步还是第 2 步；写入证据说明或证据包的 `browser/`，并能对上断言编号。
- 资金、订单、权限、登录等场景：页面证据之外仍要有接口或库等状态证据，不能只靠截图通过。

## 失败回流

验证失败时，产品逻辑问题先回流 `@@BE` / `@@FE` 定位和修复，必须回溯变更范围、实现路径和断言假设，给出修复动作；环境问题回流 `@@DEVOPS`。

如果失败暴露的是边界、方案或验收口径问题，升级 `@@BA` 或 `@@TL`。同一失败项修复和复测最多 2 轮，仍不收敛时交用户决策。

## 不允许

- 只执行开发者自验证断言，就给出重要需求通过结论。
- 环境不可用时把结论写成"通过"；只能写"验证阻塞"。
- 没有命令、实际值、断言比对结果或人工确认，就写“验证通过”。
- 有页面断言或场景，却不按「先 Playwright、再 Browser」调用、只写“建议手工验证”或等用户再说明，就给出通过结论。
- 把 Playwright 与 Browser 写成可任选、或未说明实际用了哪一个，就当作页面验证已完成。
- 只用页面截图、没有约定的后端状态证据，就给资金、订单、权限、登录类场景下通过结论。
- 没有清理方式，就忽略测试数据影响。
- 用文档证据替代验证证据。
