# 功能开发

## 通用前置检查

执行本流程前，必须先完成 `workflows/_shared/` 中的任务入口、权限、证据、验证、角色交接和完成检查。

## 目标

按 `config/rag-x-routing.yaml` 的 `role_chain` 选链路（标准链路是 `@@X -> @@TL -> @@BA -> @@BE -> @@DEVOPS -> @@QA -> @@TL`，前端改动按 `domain_substitution` 换成 `@@FE`），完成从需求到测试环境交付的收口。简单任务由 `@@X` 按流程裁剪评分走快线或简化链路。

`feature-development` 负责功能从需求到实现和测试环境验证的完整闭环；独立 `release` 只在用户任务明确是发布交付、复验已完成实现或环境交付时使用，不能替代本流程的实现与断言收口。

## 输入

- 需求描述和业务目标。
- 项目标识（如 `hx-matching`、`betwin`）。
- 目标环境（按项目 `envs.yaml` 的 `default_envs`，如 hx-matching：`dev`、`uat`；betwin：`test`）。
- 约束条件（不能动的边界、上线窗口、回滚要求）。

## 流程

```text
需求与验收口径
  → 系统/领域设计（按影响范围）
  → 契约草拟与批准（有跨领域或公共契约时）
  → 任务图校验（拆成两个以上任务时）
  → 实现与自验证
  → 集成（两个以上任务时）
  → 环境准备（需要真实环境时）
  → QA 独立验证
  → TL 技术放行
  → 知识沉淀判断
```

## 步骤

1. `@@TL` 明确目标、优先级和验收标准；跨领域或高风险时给出系统级约束。
2. `@@BA` 分析后端边界、风险、兼容点和技术取舍；涉及前端时 `@@FE` 给出前端方案。前后端都改时，接口契约由 `@@BA` 和 `@@FE` 草拟、`@@TL` 批准。
3. 要拆成两个以上任务时，`@@X` 按 `contracts/templates/task.yaml` 在 `orchestration/runs/<日期-简称>/` 下写任务契约，按 `orchestration/policies/parallelism.yaml` 判断并行类别，跑 `python orchestration/tools/task_graph_validate.py <任务目录>`；校验不过不能进入实现。只有一个任务时可以在交接块里写 `task_id`、允许修改路径和验收条件，不强制落文件。
4. `@@BE` / `@@FE` 按任务契约实现，产出实现步骤、变更文件清单、契约版本、实现质量自检、自验证结果和验证断言清单（验证项、前置条件、期望值、失败判定条件）。改动超出允许修改路径时先停下说明。
5. 两个以上任务时，`@@X` 汇总集成：同文件或公共资源冲突回到对应任务的 owner 处理，不交给 `@@TL` 统一兜底。
6. 需要真实环境时，`@@DEVOPS` 按项目内置配置准备环境，验证任务涉及组件（DB、Redis、ES、MQ 等）连通，部署冒烟，给出环境可用证据；不需要时跳过并写明原因。
7. `@@QA` 按断言清单和验收口径做独立验证；重要需求要补充真实业务场景，记录命令、实际值与证据。不能只拿开发者的自验证当通过证据。
8. 存在失败断言或场景失败时：产品逻辑问题回流 `@@BE` / `@@FE`，环境问题回流 `@@DEVOPS`；暴露边界、方案或验收口径问题时，再联动 `@@BA`/`@@TL` 后回到步骤 7 复测（最多 2 轮）。
9. 超过 2 轮仍失败，停止循环并提交给用户决策。
10. `@@TL` 按证据做技术放行，确认是否进入下一阶段。
11. `@@X` 汇总沉淀线索，`@@TL` 按 `knowledge-growth-loop` 判断是否沉淀或触发代码摘要修复。有任务目录时，按 `orchestration/README.md` 的“任务目录”收口并删除。

## 状态门槛

有任务图时，每个任务按以下状态推进，不能合并成一个"完成"：

| 状态 | 进入条件 |
| --- | --- |
| `Ready` | 依赖都满足，引用的契约都是 `approved` |
| `Implemented` | 实现者给出变更文件清单和自验证结果 |
| `Integrated` | 和其他任务合并后没有冲突，合并后能构建 |
| `Verified` | `@@QA` 断言比对和场景验证有证据，失败项已处理 |
| `Accepted` | `@@TL` 放行，或用户确认业务验收 |

`Implemented` 不代表集成成功，`Integrated` 不代表测试通过，`Verified` 不代表业务验收完成。只有到 `Accepted` 才算任务最终完成。目前状态靠交接块记录，还没有状态机工具自动拦截。

## 输出

- 架构影响说明。
- 任务图和每个任务的状态（拆成多个任务时）。
- 实现执行清单和变更文件清单。
- 断言比对报告（期望值/实际值/结论/证据）。
- 环境证据（需要真实环境时）。
- 交付结论和回滚建议。
- 问题收口记录（失败项 -> 归属 -> 修复动作 -> 复测结果）。

示例：`workflows/feature-development/examples/hx-matching-add-channel.md`。

## 收口检查

- 角色链路有会话内交接块。
- 至少覆盖一条主链路和一条失败路径。
- 重要需求要补充 3-7 个真实业务场景。
- 关键组件要说明影响对象；验证通过或给出阻塞说明。
- 交付报告可复验，且每条关键断言都有期望值、实际值和证据。
- 环境失败和产品逻辑失败分开归因。
- 失败断言必须完成“修复或阻塞决策”，不能只停在报告阶段。
- 连续 2 轮修复仍失败时，必须升级为用户决策，不允许继续死循环。
- 有可复用经验时进入 `knowledge-growth-loop`。
