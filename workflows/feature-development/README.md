# 功能开发

## 通用前置检查

执行本流程前，必须先完成 `workflows/_shared/` 中的任务入口、权限、证据、验证、角色交接和完成检查。

## 目标

通过 `@@X -> @@TL -> @@BA -> @@BE -> @@DEVOPS -> @@TL` 的协作链路，完成从需求到测试环境交付的收口。简单任务由 `@@X` 按流程裁剪评分走快线或简化链路。

## 输入

- 需求描述和业务目标。
- 项目标识（如 `hx-matching`、`betwin`）。
- 目标环境（按项目 `envs.yaml` 的 `default_envs`，如 hx-matching：`dev`、`uat`；betwin：`test`）。
- 约束条件（不能动的边界、上线窗口、回滚要求）。

## 一阶段步骤

1. `@@TL` 明确目标、优先级和验收标准。
2. `@@BA` 分析边界、风险、兼容点和技术取舍。
3. `@@BE` 产出实现步骤、改动清单、实现质量自检、BE 自验证结果和验证断言清单（验证项、前置条件、期望值、失败判定条件）。
4. `@@DEVOPS` 按项目内置配置准备环境，并执行任务涉及组件验证（DB、Redis、ES、MQ 等）。
5. `@@DEVOPS` 按断言清单执行验证；重要需求要补充真实业务场景，记录命令、实际值与证据。
6. 如果存在失败断言或场景失败，先回流 `@@BE` 定位和修复；如果暴露边界、方案或验收口径问题，再联动 `@@BA`/`@@TL` 后回到步骤 5 复测（最多 2 轮）。
7. 超过 2 轮仍失败，停止循环并提交给用户决策。
8. `@@TL` 做最终取舍，确认是否进入下一阶段。

## 输出

- 架构影响说明。
- 实现执行清单。
- 断言比对报告（期望值/实际值/结论/证据）。
- 交付结论和回滚建议。
- 问题收口记录（失败项 -> 修复动作 -> 复测结果）。

## 收口检查

- 角色链路有会话内交接块。
- 至少覆盖一条主链路和一条失败路径。
- 重要需求要补充 3-7 个真实业务场景。
- 关键组件要说明影响对象；验证通过或给出阻塞说明。
- 交付报告可复验，且每条关键断言都有期望值、实际值和证据。
- 失败断言必须完成“修复或阻塞决策”，不能只停在报告阶段。
- 连续 2 轮修复仍失败时，必须升级为用户决策，不允许继续死循环。
